# Help Desk — role-based, multilingual, voice-enabled user guides

Date: 2026-11-16
Status: Draft — reviewed, awaiting approval

## 1. Intent and why

SPIC ONE is still growing (new modules keep landing) and will be handed over to
the customer. Customers today do not understand what each page is for or how to
do their work on it, so handover and support load will be heavy.

We are adding a **Help Desk**: a plain-language guide for every screen, shown
only for the modules the signed-in user's role can use, available in several
Indian languages, and readable aloud ("Listen").

The guides must stay correct as the application changes. The rule is: **the
Help Desk changes only when the application changes**, and the person who
changes a screen updates its guide in the same change.

## 2. Goals

- A **Help Desk page** (`/Help`) listing every guide the user is allowed to
  see, grouped by module, with a search box.
- A **"?" Help button on every page** that opens the guide section for the
  screen the user is on.
- **Role filtering**: a user sees only the modules — and only the sections
  inside a module — that their role/designation can reach. An RMDO sees
  "Raise a publicity request"; a reviewer sees "Review and dispatch".
- **Languages**: English, Tamil, Telugu, Marathi at launch (the same four the
  SAS lab reports already support). Adding Hindi or another language must be a
  configuration + content step, not a code change.
- **Voice**: a "Listen" button reads the current guide section aloud in the
  chosen language with a natural Indian voice that sounds the same on every
  device (web, Android, iOS, Windows).
- **Built to grow**: a new module gets a guide by adding one folder of files.
  A check lists screens that have no guide so nothing ships undocumented.
- Works on both hosts (Web and MAUI) from the shared Razor library.

## 3. Non-goals

- Support tickets / "raise a query" workflow. (Contact Us stays as is.)
- Admin-editable guides in the database (considered and rejected — see §5).
- Translating the rest of the application UI. Only the Help content is
  multilingual.
- Video tutorials.
- AI chat help. ("Ask SPIC AI" in Digital Library is unchanged.)

## 4. Anti-goals (would be a failure even if it "works")

- A user sees a guide for a module they cannot open.
- Guides drift out of date with the screens they describe.
- Screenshots show real customer/farmer/dealer data. All screenshots use demo
  or local test data only.
- Voice reads the wrong language, or sounds robotic enough that users stop
  using it.
- A guide change forces a manual chore (re-recording audio by hand, editing
  four languages by hand) that developers will skip.

## 5. Approaches considered

| | Approach | Trade-off | Decision |
|---|---|---|---|
| A | **Guide files inside the app**, owned by developers, updated in the same change as the screen; tools generate translations and voice | Guides cannot drift from screens (reviewed together); every wording change needs a release | **Chosen** |
| B | Guides in the database with an admin editor | Customer can edit without a release, but developers changing a screen don't see the guide, and the customer's admin rewrites guides to their own needs — guides and app drift apart | Rejected |
| C | Reuse Digital Library as the help store | Cheapest, but Library is open to all and holds agri content; mixing help in confuses users and loses role filtering | Rejected |

The user picked **A** because the Help Desk should change only when the
application changes, and developers are the ones who change the application.

## 6. Design

### 6.1 Content: one folder per module

```
HelpContent/
  help.config.json                 ← languages, voices, glossary path
  glossary.json                    ← terms kept as-is or fixed per language
  publicity/
    guide.en.md                    ← source of truth, written by developers
    guide.ta.md                    ← generated by tool, reviewed, committed
    guide.te.md
    guide.mr.md
    images/                        ← screenshots (demo data only)
  sas-sample-collection/ ...
  lab/ ...
```

- **English is the source.** Other languages are generated from it by a tool
  (§6.5) and committed, so they are reviewable in a pull request.
- Each translated file records the hash of the English section it came from.
  If English changes and the translation was not regenerated, the build check
  flags it (§6.7).
- Guide text must be readable by **both** the UI (to display) and the API (to
  generate voice, §6.6). Where the files physically live so both can read them
  (e.g. embedded resources in a project both reference, or linked content
  files) is the builder's call. Images are served as static web assets from the
  shared Razor library so both hosts serve them.

### 6.2 Guide file format

Markdown with a small front-matter block. A guide is one module; it is split
into **sections**, each describing one screen or one task.

```markdown
---
module: publicity
title: Publicity Material Tracking
icon: megaphone
order: 40
---

::: section id=raise-request
title: Raise a publicity request
for: PublicityRequest
routes: /PublicityRequest, /PublicityRequest/new, /PublicityRequest/edit/{id}

**What this screen is for** — ...

**Steps**
1. Tap **New request**.
2. ...

**Fields explained** — ...

**Common problems** — ...
:::

::: section id=review-dispatch
title: Review and dispatch requests
for: PublicityReview
routes: /PublicityReview, /PublicityReview/{id}, /PublicityReview/{id}/dispatch
...
:::
```

- `routes:` — the screens this section explains. Drives the "?" button and
  the main visibility rule (§6.3). `{id}`-style placeholders match any segment.
- `for:` (optional) — narrows by action rights, using the existing
  `"Page.Action"` token format (e.g. `SampleCollection.Entry`,
  `PublicityReview.Dispatch`), checked with `LoginState.Can(page, action)`.
  Lets a view-only user skip "Collect a sample" while still seeing "View
  samples".
- `roles:` / `designations:` (optional) — **narrow only**, by AppRole or by
  designation name, for the places where behaviour inside a page is decided by
  role or designation name (e.g. Publicity dispatch is ADMIN-MD CS / DGM-MD CS
  only; Farmer-only "My Samples").
- All filters on a section must pass for it to be shown.
- Section `id`s are stable; translations and audio are keyed by them.
- Recommended section shape: *What this screen is for → Steps → Fields
  explained → Common problems*. Short numbered steps, plain words.
- Exact syntax of the section markers is the builder's call; the above shows
  the information each section must carry.

### 6.3 Role filtering

**Rule: a section is shown if the user can actually open at least one of its
`routes:`**, then narrowed by `for:` / `roles:` / `designations:`.

- Why route-level and not menu-level: the menu check (`CanSeeMenu`) and the
  route check (`CanAccess` + `PageGuard`) disagree in many places — open-to-all
  pages hidden from the menu, Dealer → SDWA and Director → SchemeApproval hard
  rules in `PageGuard`, SuperAdmin bypassing `PageGuard` entirely. The anti-goal
  is "a guide for a module they cannot open", so the truth is what the route
  lets them open. Guides then need very few `roles:` exceptions.
- To get that answer outside `PageGuard`, extract `PageGuard.razor`'s decision
  logic into a shared service (e.g. `RouteAccess.CanOpen(LoginState, path)`)
  that `PageGuard` calls and `HelpCatalog` reuses. **This must be a
  behaviour-preserving refactor** of a security-relevant component, covered by
  tests that pin today's decisions for each role before the move.
- A `HelpCatalog` service loads all guides and returns the visible sections.
  A module appears on the Help Desk if at least one of its sections is visible.
- No new permission model; no new `PagePermission` member.
- **`/Help` is open to every signed-in user, every role** — including
  CommonRole / SpecialAdmin and designation-only users like Lab staff. It goes
  in `PageGuard`'s always-open list (not `OpenAccessRoutes`, which those roles
  skip), and the Help menu entry is shown unconditionally rather than through
  `CanSeeMenu`. Users with no designation are still sent to `/Welcome` as today
  (they have no modules to read about).

### 6.4 Screens

- **`/Help` — Help Desk.** Language selector, search box, module cards
  (icon, title, number of guides). Search matches section titles and text in
  the selected language, across visible sections only.
- **`/Help/{module}` and `/Help/{module}/{section}` — guide view.** Section
  list on the left (desktop) / collapsible list (phone), rendered section with
  screenshots, a **Listen** button per section, language selector, and a
  "Open this screen" link to the section's first route.
- **"?" Help button** in the shared page chrome (top bar on desktop, header on
  phone). It resolves the current URL to the matching section via `routes:`;
  if no section matches, it opens the module's guide; if no module matches, it
  opens `/Help`. Opens as a side panel / bottom sheet so the user keeps their
  place; a "full page" link goes to `/Help/{module}/{section}`.
- **Menu entries**: "Help Desk" added in `NavMenu.razor`,
  `ShellNavigation.Candidates` and `MobileSidebar.razor`.
- Language choice is remembered per device (localStorage on web, Preferences
  on MAUI). Default: English. If a section has no translation yet, show English
  with a small "not yet translated" note.
- Guide text is bundled with the app, so reading works offline on MAUI. Voice
  needs a connection; Listen is disabled with a note when offline.

### 6.5 Translation tool

`tools/help-tools translate`:

- Reads each `guide.en.md`, finds sections whose English hash differs from the
  hash recorded in each translated file, and translates only those.
- Uses the Anthropic provider the API already uses for "Ask SPIC AI"
  (developer's own key from local config/env — never committed).
- Applies `glossary.json`: role names (RMDO, JMDO, MDO, SMM…), module names,
  button labels and terms like "Consignment" stay as they appear on screen or
  use a fixed agreed translation.
- Keeps Markdown structure, section ids, routes and image links untouched.
- Output is committed and reviewed like code.
- **Review policy (user decision):** machine translations ship straight away
  with a small "Machine translated" note on the section. The note disappears
  once a native speaker approves that section in the in-app review screen
  (§6.9). Changing the English section changes its hash, which brings the note
  back until the new translation is approved.
- **Automatic quality check (back-translation):** after translating, the tool
  translates the result back to English and asks the model to compare it with
  the original. Sections where meaning has drifted, steps are missing, or
  button/role names changed are marked `confidence: low` in the file. Low
  sections are shown first to reviewers. This narrows human review; it does not
  replace it.
- Glossary starts from the agreed terms already in
  `Spic.Infrastructure/Services/LabReports/LabTranslationSeed.cs` where they
  overlap.

### 6.6 Voice

- Voices: Azure AI Speech neural voices for en-IN, ta-IN, te-IN, mr-IN
  (hi-IN available later). Voice name per language lives in `help.config.json`.
- **Generated on demand by the API and cached**:
  `GET /api/Help/audio/{module}/{section}/{lang}`
  1. API looks up the section text from the same guide files (§6.1) —
     it never speaks arbitrary text sent by the client.
  2. Strips Markdown to speakable text, hashes it.
  3. If `Uploads/Help/audio/{lang}/{hash}.mp3` exists, streams it.
  4. Otherwise calls Azure Speech, saves the file, streams it.
- A changed guide produces a new hash, so audio refreshes itself — no manual
  re-recording, no audio files in git. `Uploads` is already on Azure Files.
- Requires `[Authorize]`. The Speech key lives in Key Vault like the other
  secrets. If no Speech key is configured (e.g. local dev), the endpoint
  returns 404 and the Listen button hides.
- Infra: a new Azure AI Speech resource. Follows the existing rule — what-if
  first, infra-only deploy path, user runs prod deploys.
- **Voice is fully automatic in every language**: it is made from whatever text
  is in that language's guide file. No one records audio. When a reviewer's
  text correction is merged, the text hash changes and the voice regenerates
  itself on the next Listen.
- **Pronunciation fixes**: English words inside Indian-language text (RMDO,
  Consignment, SAS) and numbers can be read oddly. `glossary.json` holds a
  per-language "say it as" entry for such terms; the API applies it when
  building the speech request (Azure Speech `sub`/lexicon). Reviewers report
  bad pronunciation from the review screen (§6.9); a developer adds the
  glossary entry.

### 6.7 Coverage and freshness check

`tools/help-tools check` — **run by hand by developers (user decision)**. The
repo has no CI today, and the user chose not to gate deploys on it.

- Lists every `@page` route in the shared Razor library and reports routes not
  covered by any guide section's `routes:`, grouped by module, with a count.
- An **ignore list** for pages that need no guide (login, welcome, privacy,
  about-us, account selector…).
- Exit code is non-zero when gaps exist, so it can be wired into CI or the
  deploy script later without changes.
- Flags translations whose source hash is stale.
- Flags `for:` tokens whose page is not a real `PagePermission` member, and
  image links that don't resolve.

### 6.9 Translation and voice verification (in-app review)

Reviewers are native speakers who may not be developers (ours or the
customer's), so review happens inside the app, not in git.

- **Who:** a new grantable permission `HelpTranslationReview` (appended to the
  end of the `PagePermission` enum), given through the Designation grid.
  Optionally scoped per language (e.g. a Tamil reviewer sees only Tamil) — a
  reviewer's languages are stored with their review settings.
- **Screen `/Help/Review`:** pick a language → list of sections with status
  *Not reviewed / Needs correction / Approved*, `confidence: low` first.
  Opening a section shows **English and the translation side by side**, the
  screenshots, and a **Listen** button for the translated voice.
- **Reviewer actions per section:**
  - **Approve** — the "Machine translated" note disappears for that section
    straight away, no release needed.
  - **Suggest correction** — edits the translated text in place (a plain text
    box per section) with an optional comment.
  - **Report pronunciation** — names the word that sounds wrong and how it
    should be said.
- **Storage:** review records in the database, keyed by
  module + section id + language + **source hash** (hash of the English text
  and of the translated text). An approval only counts while both hashes still
  match; if either changes, the section is back to *Not reviewed*.
- **Getting corrections into the files:** `help-tools pull-reviews` (run by a
  developer) fetches pending corrections from the API, writes them into the
  `guide.<lang>.md` files, and marks those records *Applied*. The developer
  commits and releases as usual. The guide files stay the single source of
  truth; the database only holds review status and pending suggestions.
- **Progress view:** the review screen shows per language how many sections
  are approved, so the team can see when a language is fully verified.

### 6.10 Developer rule (goes in the repo's contributor notes)

> When you add or change a screen, add or update its section in
> `HelpContent/<module>/guide.en.md` in the same change, run
> `help-tools translate`, and run `help-tools check` before merging.
> Screenshots use demo data only.

Because the check is manual, this rule is the main protection against drift.
The anti-goal "guides drift out of date" is accepted as a risk the team manages
by discipline.

## 7. Rollout

1. **Framework + pilot (English)**: route-access extraction from `PageGuard`
   (with tests), content format, `HelpCatalog`, `/Help`, guide view, "?"
   button, menu entries, check tool. Pilot guides:
   Publicity, SAS Sample Collection, SAS Lab — they already have role-by-role
   workflow notes in `docs/publicity-tracking-plan.md`,
   `docs/sas-sample-collection-plan.md`, `docs/sas-lab-portal-plan.md`.
2. **Languages**: translate tool + glossary + back-translation check; ta/te/mr
   for the pilot modules.
3. **Voice**: Azure Speech resource, audio endpoint, Listen button,
   pronunciation glossary.
4. **Verification**: `HelpTranslationReview` permission, `/Help/Review`
   screen, review records (one small migration), `help-tools pull-reviews`.
5. **Remaining modules** in batches (order to be agreed with the user, likely by
   what the customer uses first).

## 8. Constraints

- Shared Razor library only; no host-specific pages. Must work on Web, Android,
  iOS and Windows.
- No new permission model; reuse `PagePermission`, `LoginState`,
  `PageAuthorization`.
- No live data in screenshots or in any test.
- Prod deploys are run by the user; infra changes go what-if first.
- Secrets (Anthropic, Azure Speech) never committed.

## 9. Decisions log

User decisions:
- Approach A (guide files in the app, developer-owned).
- Languages at launch: English, Tamil, Telugu, Marathi, Hindi (Hindi added 2026-11-16).
- Coverage check runs by hand only (no CI / deploy gate).
- Machine translations ship labelled; native review clears the label later.
- Add an in-app way for native speakers to verify translations and voice
  (§6.9); voice is generated automatically from each language's text.

Calls made during design review (open to correction):
- Visibility is **route-level** ("can the user open this page"), not
  menu-level, via a behaviour-preserving extraction of `PageGuard` logic.
- `/Help` is open to every signed-in user with a designation, via `PageGuard`'s
  always-open list; menu entry shown unconditionally.
- Section filters: `routes:` decides; `for:` (Page.Action), `roles:`,
  `designations:` only narrow.
- Voice audio generated lazily by the API and cached on Azure Files, not
  committed to git.

## 10. Left to the builder

- Where the guide files live so both UI and API read them (§6.1).
- Markdown renderer (e.g. Markdig) and exact section-marker syntax (§6.2).
- Look and feel of the Help Desk and guide view, following existing shell
  components and design tokens.
- How the "?" button is placed in the existing chrome on each form factor.
- Tool implementation (console app under `tools/`, language of choice that
  fits the repo).
